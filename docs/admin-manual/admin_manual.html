いちご在庫 管理者マニュアル

店舗管理者・保守担当者用 ／ 2026年8月版
この仕組みが保証していること
在庫は「差分の足し算」だけで動きます。「在庫を◯個にする」という命令はコードのどこにも存在しません。 そのため、農家が入荷を書いている最中に商品が売れても、売れた分が消える（売り越し）ことは構造的に起きません。
農家ファイル（入荷を書く） │ 10分ごと ▼ Shopify 在庫 ←──── お客様の注文で自動的に減る │ 10分ごと / 30分ごと ▼ マスター（Products・販売履歴・在庫台帳） │ 2時間ごと ▼ Health（異常なら管理者にメール）

第1部　毎日の運用

1-1. マスターの4つのタブ

タブ中身
Products全商品のSKU・販売元・現在の在庫（10分ごとに自動更新）

Config販売元と農家ファイルの対応表。ここを触ると同期対象が変わります

1-2. 毎朝の確認（30秒）

判定意味すること
OK正常なし
WARNエラー行が残っている農家ファイルのエラー行を確認（1-4参照）。急ぎではない
ALERT同期が止まっている／入力が反映されていないその日のうちに対応。第3部の復旧手順へ

異常のときは自動でメールが届きます（6時間に1通まで）。毎週月曜には正常でも「正常です」のメールが1通届きます。 月曜のメールが来なかったら、監視自体が止まっている可能性があります。

1-3. メニューでできること

どれも「今すぐやる」ためのものです。使わなくても自動で回ります。

1-4. 農家から連絡が来たとき

農家の画面の表示対応
ERR SKU未解決(0件)農家がSKUを直して処理状態を空にすれば直ります。直らない場合はShopify側のSKU未設定を確認

STUCK …要注意。第3部 3-4 の手順で対応してください。安易に消すと二重に加算されます

第2部　変更したいとき

2-1. 商品を増やしたとき

  1. Shopifyで商品を作る
  2. SKUを必ず設定する（例 ICH-011）。SKUがないと同期できません
  3. 販売元（vendor）に農家名を入れる。これで自動的にその農家の担当になります
  4. 10分待つと Products と農家の「商品一覧」に出ます
販売元がこれまでに無い新しい名前のときは、その農家のファイルがまだ存在しません。 第2部 2-2 の手順が必要です。

2-2. 農家を増やすとき

  1. Shopifyで、その農家の商品の販売元に農家名を入れる
  2. Apps Scriptで setupWorkspace() を1回実行 → 農家ファイルが自動で作られ、Configに行が増えます
  3. 続けて setupSalesSheets() を1回実行 → 販売履歴・在庫台帳が作られます
  4. メニュー「農家ファイルのURLを表示」でURLを出し、その農家だけに「編集者」で共有
  5. 農家用マニュアルを渡す

2〜3の実行は Apps Script の操作になります。不慣れな場合は保守担当へ依頼してください。

2-3. 農家をやめる・入れ替えるとき

マスターの Config からその行を削除すると、同期の対象外になります（ファイル自体は残ります）。 商品の販売元を別の農家名に変えれば、次の同期から新しい農家の担当になります。SKUは変えないでください。

第3部　保守（Googleアカウント所有者向け）

3-1. 構成

もの内容
スプレッドシートマスター1つ ＋ 農家ごとに1つ。コードはマスターにだけ入っています
コードApps Script 4ファイル：Code / Setup / Sales / Ops
トリガーrunSync（10分）· syncSalesHistory（30分）· dailyHealthCheck（2時間）
設定値スクリプトプロパティ：SHOPIFY_STORE / SHOPIFY_CLIENTID / SHOPIFY_SECRET / ADMIN_EMAIL

3-2. トリガーの確認

3-3. 調査は「実行履歴」だけを信用する

実際にあった事故：エディタの表示は目的の関数になっていたのに、 実行されていたのは別の関数でした。画面が「完了」と出ていても、その関数が走ったとは限りません。 必ず実行履歴で、関数名・開始時刻・ステータスを確認してください。

3-4. STUCK 行の直しかた

「送信したかどうか分からない」状態の行です。判断を間違えると二重加算になります。

  1. その行のSKUと数量を控える
  2. Shopifyの在庫を見て、その数が既に反映されているか確認する
  3. 反映済み → 処理状態を OK 手動確認 に書き換える（再送させない）
  4. 未反映 → 処理状態を空にする。次の同期で送られます

3-5. 止まったときの復旧

  1. 実行履歴を見る。エラーが出ていれば内容を読む
  2. トリガー一覧を見る。3本揃っていなければ installTrigger() / installSalesSyncTrigger() / installHealthCheckTrigger() を実行して作り直す
  3. Shopifyの認証で失敗している場合はスクリプトプロパティを確認
  4. シートを作り直すときは setupWorkspace() → setupSalesSheets()。 どちらも何度実行しても安全です（既存を壊しません）

3-6. 変えてはいけない設計

  1. 在庫は差分加算のみ。inventorySetQuantities（絶対値）を足さないこと。足した瞬間に売り越しが起きます
  2. 販売履歴と入荷入力を同じ表にしないこと。販売行が「未処理の入荷」と見なされ、二重に減算されます
  3. ロックは1箇所だけ。Apps Scriptのロックは入れ子にできず、内側が黙って何もせず終わります
  4. 監視からShopifyを呼ばないこと。Shopifyが落ちている時こそ監視は動く必要があります
  5. 週1回の正常メールを止めないこと。異常時のみ通知だと、監視が死んだ沈黙と正常な沈黙を区別できません
  6. 農家の振り分けは販売元（vendor）で行うこと。SKUで振り分けると、SKU変更前の古い注文を取りこぼします
  7. Productsシートは取得に成功してから書き換えること。先に消すと、通信障害でマスターが空になります
