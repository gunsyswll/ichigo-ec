① 在庫販売　実際の画面と操作　— 商品ページから決済完了まで（稼働中）

1. 商品ページ/products/standard-strawberry-box
  1. 1予約のように見えるが、これはただの固定テキスト。中身は通常の在庫販売
  2. 2数量を選ぶ
  3. 3「Reserve Now」でカートに入る。この時点では在庫は減らない
2. カート/cart
  1. 1入れた商品と金額
  2. 2数量はここで変えられる（0にすれば削除）
  3. 3「Checkout →」で決済画面へ
3. チェックアウト（上半分）ここから Shopify の画面。デザインは触れません
  1. 1PayPalなら、住所入力を飛ばして一発で終わる
  2. 2メールアドレス（注文確認の送り先）
  3. 3お届け先。国は Philippines 固定
  4. 4右側に合計金額が常に出ている
4. 配送方法・支払い同じページを下にスクロールしただけ。画面は変わりません
  1. 1送料は仮の値。「実運賃が未確定」とお客様に見えている
  2. 2テスト決済の説明がお客様に見えている（本番の決済を入れれば消える）
  3. 3PayPal も選べる
  4. 4「Pay now」で注文成立＝ここで在庫が確定的に減る
売り越しが起きない理由。農家が入荷を書いてもコードがShopifyに送るのは「＋5個」という差分だけで、 「在庫を15個にする」という命令はどこにもありません。同期の途中でお客様が1個買っても、その1個は消えません （注文 #1003 で実測確認済み：15→14 のあと同期が走っても 14 のまま）。 なおカートは取り置きではないので、残り1個を2人が同時にカートへ入れたら、先に決済した方だけが買えます。

③ サブスク販売　実際の画面と操作　— 毎月くり返す（プランは設定済み／ただし現状は購入できません）

1. Club の商品ページ/products/japanese-strawberry-club
  1. 1「One-time purchase」＝1回だけ買う（初期選択）
  2. 2「Deliver every month」＝毎月お届け。操作の違いはこの1クリックだけ
    ⚠ ただし金額が表示されていません。お客様は毎月いくら引かれるか分からない状態です
  3. 3選んだ状態で「Reserve Now」＝定期プラン付きでカートへ
2. チェックアウトカート〜決済画面は在庫販売と同じ。中身だけが変わります
  1. 1「First shipment」＝初回の配送
  2. 2「Recurring shipments」＝2回目以降。毎月くり返す旨がここに出る
  3. 3決済手段が1つも表示されない。「This store can't accept payments right now.」
  4. 4「Pay now」は灰色のまま。押せません
  5. 5毎月かかる金額（₱4,700／月）はここに出る
実際に操作して分かったこと：サブスクは、いまこのストアでは購入を完了できません。 通常商品なら同じ画面にクレジットカードと PayPal が出るのに、カートに定期商品が入った瞬間に決済手段がゼロになります。 いまの決済がテスト用（bogus）で、定期課金に必要なカード情報の保存に対応していないためです。 契約が0件なのはテスト不足ではなく、そもそも決済できないからでした。 解消には本番の決済（Shopify Payments）の登録が必要です — これは既に Pending #3 にある未着手項目です。
決済が通るようになった後に効いてくる点：定期の2回目以降も、ふつうの注文として在庫を食います。 契約が10件あれば毎月10箱ぶんの在庫が要ります。足りないと自動注文が失敗し、その月の売上が落ちます。 毎朝の Health チェックでは検知できません（契約件数は Shopify 側にしかないため）。
Club の販売元は Ichigo のため、サブスクの売上は農家ファイルには出ません（Pending #32）。

② 予約販売　— 先に売り、収穫後に届ける（仕組みは未実装。表示だけが予約になっています）

いま「予約」に見えている画面（＝在庫販売の画面そのもの）
  1. 1「NEXT ARRIVAL / RESERVATION DEADLINE / DELIVERY WINDOW」はテーマの設定に手で書いた固定文字で、 商品や在庫とはつながっていません。日付も 2025年のままです
  2. 3ボタンも「Reserve Now（予約する）」。しかし押した先は通常の購入で、在庫が0になった瞬間に「Sold Out」と出ます

つまりお客様は予約だと思って買い、店は在庫販売として売っている状態です。作り方を決めれば、この食い違いは解消できます。

作り方は3案。どれを取るかで運用が変わります

案A　予約枠を在庫として登録推奨

収穫予定数をそのまま在庫数として入れる。仕組みは今のままで、商品ページに発送予定日を出すだけ。

  • 追加アプリ・追加費用ゼロ
  • 枠が埋まれば自動で受付終了
  • 今の在庫同期と売り越し防止がそのまま効く
  • 農家シートも今のまま（枠の残りが在庫数に見える）
  • 全額前払いのみ（内金は不可）
  • 予約締切は「商品を非公開にする」運用で行う

案B　在庫マイナスを許可

在庫ポリシーを CONTINUE に変え、0を切っても売れるようにする。マイナス値がそのまま受注残になる。

  • 枠数を先に決めなくてよい
  • これも追加費用ゼロ
  • 農家の画面に「−7個」と出る（説明が要る）
  • 上限が無い。採れなかったら全件キャンセル・返金
  • 「売り越しが構造的に起きない」という今の性質を捨てることになる

案C　予約アプリを入れる

内金・分割課金・予約締切の自動化が必要な場合のみ。月額のかかる有料アプリになる。

  • 内金だけ先に取り、残りは発送時に課金できる
  • 締切・上限・バッジ表示が自動
  • 月額費用が発生する
  • 課金が2段階になると在庫が減る瞬間がアプリ依存になる。今の同期の前提を検証し直す必要がある
推奨は案A。いちごは収穫量がある程度読める季節商品なので「今シーズン何箱出せるか」＝予約枠が自然に決まります。 枠を在庫として持てば、これまで作った売り越し防止・在庫同期・農家シートを1行も変えずに予約販売ができます。 こちらの作業は「商品ページの発送予定日を、商品ごとの値として出す」だけです。
お客様側の画面・操作は3案とも同じです。違うのは店側の運用と、在庫がマイナスになるかどうかだけです。
