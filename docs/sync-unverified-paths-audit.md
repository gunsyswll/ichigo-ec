## 1–2. ページング — 実APIで検証済み

「100件を超えたときにページングが正しく回るか」は商品が10件しかないので通せない。
そこで **本番コードと同一のクエリ式を実APIに投げ**、2つに分けて確かめた。

### A. 本番の `first:100` がそもそも受理されるか（コスト上限）
ネストした `variants(first:100)` / `lineItems(first:100)` はクエリコストを押し上げるため、
**ページングが始まる前にコスト上限で落ちる**可能性があった。実測:

| クエリ | requestedQueryCost | 上限 | 判定 |
|---|---|---|---|
| `products(first:100){variants(first:100)}` | **191** | 2000 | 余裕あり |
| `orders(first:100){lineItems(first:100)}` | **110** | 2000 | 余裕あり |

Shopify のコスト見積りは単純な掛け算ではなく、実測値は上限の1/10以下。商品や注文が増えても
このクエリ形のままで問題ない。

### B. カーソル追従ロジックそのもの
本番と同じ式（`hasNextPage ? endCursor : null`）で、**ページサイズだけを小さくして**実走した。

- 商品: `first:2` で **5ページ**を追従 → SKU 10件、**重複0・欠落0**。
  `first:100` の一括取得と**完全一致**（ICH-001〜ICH-010）。
- 注文: `first:1` で **3ページ**を追従 → #1001 / #1002 / #1003、重複0。

ページ境界をまたぐ動作そのものが確認できたので、件数が増えたときも同じ経路を通る。

⚠️ **残る限界（低リスク・記録のみ）**: `variants(first:100)` に**内側のページングが無い**。
1商品に100を超えるバリアントがあると、101件目以降は**エラーにならず黙って落ちる**。
現在は全商品1バリアントなので影響なし。サイズ×等級で組合せを増やす場合はここを直す。

## 3. ロック競合 — 監査で妥当

`pushPendingAdjustments` / `syncProductsFromShopify` / `syncSalesHistory` の3つとも
`LockService.getScriptLock()` → `tryLock(30000)` → **`finally` で `releaseLock()`**。
入れ子は無い（`runSync` は2つを順に呼ぶだけで、自身はロックを取らない）。

⚠️ 3つは**同じスクリプトロックを共有**するため、在庫同期が長引くと**販売履歴の同期が
黙ってスキップ**されうる（30秒待って `return`）。これは設計どおりの安全側の挙動だが、
気づけないと困る。**Health の H2（販売同期の鮮度 > 6時間）が受け止める**ようになっている。

## 4. `ADMIN_EMAIL` 未設定 — 🔴 バグを発見、修正済み

`Ops.gs` は「未設定なら送らず Health に記録する」と正しく書かれていたが、
**`Code.gs` の `notifyAdmin` は無防備**だった:

```js
MailApp.sendEmail(CONFIG.ADMIN_EMAIL, 'Shopify Sync Alert', message);
```

`ADMIN_EMAIL` が未設定だと `MailApp.sendEmail(null, ...)` が**例外**になる。
`notifyAdmin` は `reportStuckSending` と各エラー経路から呼ばれるので、
**「通知できない」が「同期が落ちる」に化ける**。しかもエラー通知の最中に落ちるので、
落ちたこと自体も通知されない。`Code.gs` 冒頭の設計メモにある
「代替の宛先を発明しない」という規則にも反していた。

**修正（`sheets-sync/Code.gs`、リポジトリ側は適用済み）**: 宛先が無ければ送らず、
`Log` に `WARN ADMIN_EMAIL 未設定` を残して正常に戻る。あわせて宛先を
`CONFIG`（スクリプト読み込み時に1回だけ取得）ではなく**毎回プロパティから読む**ようにしたので、
設定を変えたときに次の実行から効く。

⚠️ **Apps Script 側への反映にはコピペが1回必要**（クリップボード貼り付けはブラウザ拡張から
注入できず、直接タイプはエディタの括弧自動補完で壊れるため）。→ Pending に登録。

## 5. STUCK 行の復旧 — ⛔ 実行できず

「`SENDING <uuid>` のまま止まった行が STUCK に変わり、Log とメールで気づける」経路。
検証には**農家ファイルに `SENDING …` の行を1行書く**必要があるが、
スプレッドシートへの書き込みが権限で拒否されたため実行できなかった。

コード上は正しい（`reportStuckSending`）:
- 列Eが `SENDING ` で始まる行を全農家から集める
- `Log` に1行ずつ `stuck SENDING` として記録
- **`SENDING ` → `STUCK ` に書き換える**（毎回再ログされてLogが埋まるのを防ぐ）
- `STUCK` も非空なので**自動再送は絶対に起きない**（人が列Eを空にして初めて再送）
- `flush()` してから `notifyAdmin`

**確実に検証するには**（所要1分・オーナー作業）:
1. 農家ファイル `入荷入力` の空行に `日付 / ICH-001 / 1 / STUCKテスト` を書き、
   **列E（処理状態）に `SENDING test-0811` と手で入れる**
2. マスターのメニュー「いちご同期 → 今すぐ同期 (入荷を反映)」
3. 期待: 列Eが **`STUCK test-0811`** に変わる／`Log` に `stuck SENDING` の行／
   在庫は**動かない**（列Eが非空なので送信対象外）
4. 後始末: その行を削除

## まとめ

- ページング2件は**実APIで実走して確認**（コスト上限にも余裕あり）
- ロックは監査で妥当。共有ロックによる販売同期スキップは H2 が受け止める
- `ADMIN_EMAIL` 未設定で**同期ごと落ちるバグを発見・修正**（要コピペ1回）
- STUCK 復旧だけは実行手段が無く**未検証のまま**。上の4ステップで潰せる
